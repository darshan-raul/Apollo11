# Learner flow review — code and lifecycle crosscheck

Reviewed 2026-10-05. This supporting review compares the adjoining learning site with the Apollo11 lab source. It proposes changes; it does not modify the curriculum or certify a live lifecycle. Sources are local first-party documentation, manifests, and scripts. All proposed manual build sequences and new fixtures, including the deterministic PDB and bounded slow-request alternatives, are design recommendations that have not been run or validated. Current gap fixes remain pending live verification, as recorded in [GAP_CLOSURE.md](./GAP_CLOSURE.md).

## Main finding

The requested direction is compatible with the approved roadmap: raw resources are the learning surface through Stage 4; Helm becomes canonical in Stage 5; mechanisms must be built and proved through behavior. The major change is to make implementation the required stage journey, with failures integrated into that journey, rather than an optional collection of exercises after conceptual reading. [ROADMAP.md](/home/darshan/projects/Apollo11/ROADMAP.md:18) already requires Build → Inspect → Break → Recover → Explain. [How to use this course](/home/darshan/projects/apollo11-docs/docs/start/how-to-use-this-course.md:26) currently permits moving from chapters/checkpoint straight to the next mission without implementing anything. That completion model must change for the practical curriculum the user requests.

Preserve the full working snapshots as reference solutions and maintainer reproducibility paths. The stage installation scripts already expose valuable dependency ordering, but reading what the script does is not equivalent to choosing fields, authoring resources, applying them, and diagnosing the result. Separate prerequisite preparation from applying learner-owned resources. Installing a vendored controller bundle is reasonable infrastructure preparation; automatically creating every resource whose semantics the stage teaches defeats the stage outcome.

## Specific experiment corrections

### Ignition: retain the actor distinction, change how it is learned

[The Pod command](/home/darshan/projects/Apollo11/stages/ignition/pod.yaml:13) starts `httpd` as a child and waits for it; killing the child terminates the supervising container process. Thus [Exercise 4](/home/darshan/projects/apollo11-docs/docs/ignition.md:434) has a valid process-recovery mechanism. Its educational weakness is presenting an already finished environment and a command to execute without enough authorship or investigation.

Replace the standalone exercise with an implementation checkpoint: learner writes the Pod and identifies restart policy; records UID, container ID, restart count, node and an HTTP response; predicts who will repair a process failure; performs the failure; obtains previous-container logs and compares recorded evidence; then deletes the bare Pod and diagnoses why no controller creates another. Require learner reapplication and a new HTTP response. Explain the `wait` relationship explicitly so learners do not conclude that Kubernetes restarts any failed child process. Restart policy applies when the container terminates, not to arbitrary child failures inside a still-running container.

### Stage 3: storage proof is narrower than disaster recovery

[The stage manifest](/home/darshan/projects/Apollo11/stages/stage3/k8s/apps/identity-db/identity-db-sts.yaml:73) uses a PVC template without an explicit StorageClass. [The README](/home/darshan/projects/Apollo11/stages/stage3/README.md:278) documents the kind local-path default. Pod deletion proves reuse of persistent data on its existing storage; it cannot prove data survives loss of the Docker host or local disk. Learners must record PVC/PV linkage and node affinity rather than infer “StatefulSet means durable everywhere.”

[Stage 3 Exercise 4](/home/darshan/projects/apollo11-docs/docs/stage-3.md:446) is inspection only: it explicitly does not delete a PVC or PV. Rename its outcome to reclaim-policy inspection, or implement a separate disposable claim with a marker and owner-scoped cleanup. Do not delete application PVCs to make the topic hands-on. The lab must demonstrate retention and reclamation with appropriate provisioning and cleanup if it advertises both behaviors.

### Stage 4: eliminate timing-dependent PDB assessment

[Docs eviction instructions](/home/darshan/projects/apollo11-docs/docs/stage-4.md:389) and [maintainer verifier](/home/darshan/projects/Apollo11/stages/stage4/scripts/verify.sh:429) immediately evict one Pod and then another. Replacement readiness can restore the budget before the second request. The docs acknowledge the race but still prescribe an expected rejection.

Use a deterministic reduced-availability condition instead. For example, in an isolated learner instance with no HPA/GitOps controller, set booking replicas to one, wait until exactly one selected Pod remains Ready and the PDB reports zero allowed disruptions, and issue one eviction to prove rejection. Then restore two healthy replicas, verify the budget allows one disruption, and demonstrate one allowed eviction. Record original replicas and restore them. This proves the contract without asking the learner to win a race. Do not use direct Pod deletion as proof of PDB enforcement.

### Stage 4: a shutdown log does not prove request draining

[The shutdown experiment](/home/darshan/projects/Apollo11/stages/stage4/README.md:110) records SIGTERM; [the recovery instructions](/home/darshan/projects/Apollo11/stages/stage4/README.md:145) issue one health request afterwards and say traffic continued uninterrupted. Neither establishes an in-flight request completed through shutdown or that every request remained available.

For an availability claim, collect a timestamped sequence of actual booking-service responses before/during/after deletion and compare failures. For draining, use a bounded, observable long-running request in a disposable instance, send SIGTERM after the request has demonstrably started, and prove that request returns successfully before the old process exits. If the application has no safe slow request, add a lab-only bounded mechanism or narrow the lesson to observing termination rather than promising drain proof. These are source/lab changes, not a heading rewrite.

### Stage 7: observed caching and scale-out are separate claims

[The benchmark](/home/darshan/projects/Apollo11/stages/stage7/k6/README.md:24) already saves HPA state, fixes replicas, disables/enables cache, requires populated results and compares both summaries. Reuse these controlled variables in the required learner build flow. Do not equate `X-Cache: HIT` with improved latency: the guide explicitly allows measured latency not to improve. Keep date/seed validity checks so empty fast responses cannot pass as optimization.

[The scaling script](/home/darshan/projects/Apollo11/stages/stage7/scripts/scaling-lab.sh:152) applies node policy and lowers the HPA target for the demonstration. Unpack each action into learner steps and make the changed threshold visible. Avoid suggesting scale-out under a lowered 10% target validates a production 70% policy. Its cleanup removes matching labels/taints from all worker nodes rather than preserving arbitrary pre-existing values ([cleanup implementation](/home/darshan/projects/Apollo11/stages/stage7/scripts/scaling-lab.sh:49)); use a disposable cluster or improve exact state preservation before promoting the sequence into a general manual lab.

## Resource authorship and lifecycle guardrails

1. Provide learner-owned working files and a separately linked finished solution. The learner edits one resource or small related set, validates it, applies it and proves behavior before the next addition. Avoid another complete stage snapshot for every checkpoint.
2. Define what the learner authors and what is supplied. Supply application code, SQL, pinned third-party controller bundles and certificate tooling when they are prerequisites; learners implement the Kubernetes resources and configuration relationships that the stage teaches.
3. Give every stage an entry contract: source revision plus patch status, cluster/context, namespace, image tags/build flags, active controllers, baseline data and required tools. A manually authored resource must still satisfy frontend build-time URL and certificate ownership contracts.
4. Specify transition/ownership: raw manifests through Stage 4; release ownership for Helm; generated base for Kustomize; Git ownership for Argo; HPA ownership of replica count. Do not let multiple reconcilers silently undo a manual learning step.
5. Put context-explicit commands, bounded waits, expected failure interpretation, exact original-state restoration and residue checks into the required flow. An installer/verifier's context guard does not guard later bare `kubectl` commands.
6. Reserve `verify.sh` for maintainer reproducibility or an optional final diagnostic after learner evidence is collected. Verifiers may mutate the cluster; they are neither reading-only assessment nor a replacement for learner implementation. A separate observational checkpoint tool could be useful but must not create, repair or conceal failures.
7. Retain checkpoint evidence: authored diff, API acceptance, reconciled status, real behavior, failure evidence, restored behavior and explanation. Per-stage passing totals remain historical until the current revision passes a clean lifecycle.
